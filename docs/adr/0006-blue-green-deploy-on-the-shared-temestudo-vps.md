# Blue/green deploy on the shared temestudo VPS

filmes goes online at `cinema.temestudo.cloud` on the VPS that already serves temestudo.cloud (temestudo-app, temestudo-stats) and saude.temestudo.cloud (saude-app), a Hostinger KVM 1. The deploy is pesquisa-relacionamentos' (`deploy-plan.ts`, `vps.ts`, `check-live.ts`, `prepare-vps.sh`, the wizard), adapted. It first went up at `cinema.finalsend.com.br`; on 2026-11-24 the user moved it to the temestudo domain, where the VPS already lives, and that name was deleted.

## Decision

- **A Docker container behind the host's Nginx, swapped blue/green.** `frontend/scripts/deploy-plan.ts` builds the bash each step runs; `vps.ts` runs it over SSH. The image `filmes-app:sha-<sha>` is built on the VPS from the uploaded `.output`. The new container starts on the free port of the pair 3091/3092, Nginx only passes to it after `/` answers, and the old one stops after the reload. The VPS keeps the previous image for `--rollback`.
- **Everything is filmes' own, and nothing else is touched.** Folder `/opt/filmes`, container `filmes-app`, vhost `sites-available/filmes.conf`, include `/etc/nginx/filmes/filmes-app.conf`, log format `filmes_without_query` in `conf.d/filmes-log-without-query.conf`, TLS cache `filmes_tls`, rotation `/etc/logrotate.d/filmes`, logs in `/var/log/nginx/filmes/`, certificate `cinema.temestudo.cloud`, and an SSH key of its own (`filmes-deploy`) in root's `authorized_keys`. The vhost never declares `default_server` (temestudo's has it on 80 and 443), and no script removes `sites-enabled/default`, another site's file or another image. The ports avoid 3011/3031 (temestudo), 3051 (stats) and 3071 (saude). `vps.test.ts` runs the plan on a fake VPS that already serves temestudo and checks it is left as it was.
- **The volume is `/opt/filmes/data`, mounted at `/data`**, owned by the image's `node` user (UID 1000): `db/<version>.sqlite` for the database versions `db:publish` ships (ADR 0005), and `auth.sqlite` and the sources' cache beside them, outside the swap. The container is otherwise read-only.
- **A database version is swapped like an image.** `pnpm db:publish <file>` (`frontend/scripts/db-publish.ts`) sends the SQLite with rsync to `db/<version>.sqlite.part`, renames it once its header and size check out, and starts the live image on the free port with `FILMES_DATABASE=/data/db/<version>.sqlite`. `/opt/filmes/db-live` and `db-previous` name the versions, as `live` and `previous` name the images; every app swap passes `db-live` on, so a code deploy keeps the database and a database publish keeps the code. The VPS keeps the live and the previous version, for `db:publish --rollback`, and deletes the rest of `db/`. The upload stops first when no app is live, the version exists, or the disk would keep less than 1 GB free.
- **The database is built from an older filmes-dados than the app's, so the app reloads on start.** `db:publish --build` builds the file on servidor-azul with the engine's `rebuild` in a process of its own (`frontend/scripts/db-rebuild.ts`), from a scratch copy of filmes-dados and the config migrated to English (`frontend/scripts/db-build.ts`); `--python` builds with the Python engine instead, from copies migrated to Portuguese, until Python leaves (#108, ADR 0004). The checkout and the repo's `config/` stay as they are. The dumps it reads are the ones `pnpm catalog:update` (the engine's `update`, Python's `atualizar`) downloaded and pinned in the config's manifest. Between that snapshot and the swap the VPS keeps writing Pessoas, imports and Sessions, so the server reloads them from filmes-dados into the database before it answers its first request (`reloadData`, `frontend/src/platform/engine.ts`): the loading steps of a rebuild over the rows the build put there. The database file must stay writable by the container. The image carries the engine's config in English at `/app/config` (`FILMES_CONFIG`), bundled by `pnpm build`; the sources' cache is `/data/cache.sqlite`, outside `db/`.
- **The database is in WAL mode** (#125), so `evaluate`'s read transaction of minutes never blocks a write (a Feedback, an import). Both rebuilds switch the file to WAL after the build and close it, which checkpoints it: `db:publish` ships one file, and refuses one with a non-empty `-wal` or `-journal` beside it. The engine's `write` switches a file built before that, so an older version comes up in WAL at the first write of the start reload. On the VPS the container (user `node`, owner of `db/`) creates `<version>.sqlite-wal` and `-shm` beside the file in the bind-mounted volume; they belong to that version: retention keeps them for the live and the previous version (a rollback opens the file with its committed pages) and deletes them with the rest. During a swap both containers share them, which WAL allows for processes on one host. Never copy the file alone while the app runs: use SQLite's backup.
- **DNS:** an unproxied (grey) A record on Cloudflare, so certbot validates by webroot on the VPS (`/opt/filmes/acme`).
- **GitHub Actions deploys every push to `master`** that changes the app (`.github/workflows/deploy.yml`), and `check-live.ts` checks the site from outside. Without the `VPS_*` secrets the publish is skipped with a warning.

## Why

The VPS has room (1 core, 3.9 GB, 41 GB free) and filmes has two users. A second VPS would cost money and a second set of keys for nothing. Sharing it is only safe if a mistake in filmes' deploy cannot take temestudo or saude down: hence the separate names, the absence of `default_server`, `nginx -t` with undo before every reload, and the test on a VPS that already has neighbours.

## Consequences

- A change to a name above breaks the next swap or rollback on the live server; rename only with a migration step in the plan. That includes `db-live`, `db-previous` and `FILMES_DATABASE`.
- `systemctl reload nginx` is shared: an `nginx -t` failure on the VPS caused by another site's file also stops filmes' deploy, and the reverse is prevented by the undo.
- Rotating temestudo's deploy key does not affect filmes, and the reverse.
