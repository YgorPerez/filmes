# DuckDB for the catalog database: `recomendar` on the real database (#124)

2026-11-25, servidor-azul. Question from #124: on the real database, does DuckDB make `recomendar` at least 2× faster at p95, end to end, than today's TypeScript engine on SQLite?

**Answer: no-go.** DuckDB is slower at p95: 19.1 s against 14.8 s for SQLite over every run (0.78×). It is ahead only on cold runs (p95 19.3 s against 25.2 s, 1.30×), and even there it is short of 2×. DuckDB computes the heavy statements 3–7× faster than SQLite. But `recomendar` hands about 2.3 million rows to JS per request, and turning DuckDB's result into JS rows costs more than SQLite's whole statement.

## Setup

- **Data.** A copy of the real database, taken with a read-only `node:sqlite` backup into a scratch folder. It had 147,705 films, 10.5M genome rows and 1.8M edges. The copy was converted to DuckDB with the `sqlite` extension: one `CREATE TABLE … AS SELECT` per table, then the three views, the 18 SQLite indexes, and each table's primary key as an ART index. The conversion took 116 s with a 1.2 GB peak RSS. The source cache was copied too. Every copy has been deleted.
- **Engines.** Both sides run the same TypeScript `recommend` from `origin/spec/72-port` (5982613). Only the `Sqlite` service under it changes:
  - The SQLite side is today's `Sqlite.layer` (`node:sqlite`), with each statement timed.
  - The DuckDB side is `research/124-duckdb/duck-sqlite.ts`. It implements the engine's own `Connection` seam on `@duckdb/node-api` 2.0.1-r.1, with `memory_limit` 1GB, 2 threads, a `temp_directory`, `access_mode` READ_ONLY and SQLite's NULL order.
  - The SQL is the engine's, rewritten at prepare time in only two ways: `json_each(?)` becomes `unnest(from_json(?, '["VARCHAR"]'))`, and `?N`/`?` become `$N`. `recommend` calls none of the JS SQL functions, so neither `ln` nor `dobrar` was needed. Rows come back through `getRowObjectsJS`, as the engine reads them (row objects).
- **Requests.** 32 requests from a fixed seed (124). They use the shape of #84's generator (`oracle/real/plan.ts` on `ticket/84-real-oracle`):
  - mulberry32; the Regra cycles through default, average and by;
  - a Clima 60% of the time;
  - the 56 restriction sets (none, each of the 10 alone, each pair), cycled;
  - 20 films per request.
  - Presentes: 3 to 5, which means 3–4, because the real database has 4 Pessoas.

  The run calls `recommend` without opening the Session: the Session write is a small SQLite write that this measurement does not compare.
- **Interleaving.** Each engine runs in its own long-lived process, and `bench.ts` drives the two over stdin. The two engines alternate request by request, and the engine that goes first alternates too, so the machine's load hits both alike.
- **Passes.** There were 2 rounds. Each round started by evicting both database files from the page cache (`posix_fadvise DONTNEED`), then started fresh processes and ran 2 passes: pass 1 is **cold** (new process, files out of the page cache) and pass 2 is **warm**. In total, each engine ran 128 requests.
- **Load.** The machine was shared with other sessions throughout (8 cores, 23 GB). Load average (1 min) during the run: min 5.6, median 7.7, max 21.5.

## Results

`recommend` wall time per request, in seconds. The 4 requests that fail on both engines are left out of the timings: one restriction pair asks for `--desde` after `--ate`, and both engines refuse it with the same usage error. That leaves 124 requests per engine.

| run | SQLite p50 | SQLite p95 | DuckDB p50 | DuckDB p95 | SQLite/DuckDB p50 | SQLite/DuckDB p95 |
|---|---|---|---|---|---|---|
| cold | 8.89 | 25.22 | 11.52 | 19.33 | 0.77× | **1.30×** |
| warm | 8.33 | 12.56 | 10.79 | 17.82 | 0.77× | **0.71×** |
| all | 8.58 | 14.83 | 11.32 | 19.09 | 0.76× | **0.78×** |

Paired by request (same request, round and pass), SQLite time divided by DuckDB time has a median of 0.77×, with p5 0.52× and p95 1.29×. The 2× target needs a ratio of 2.0 or more. No paired request reached it.

The cold SQLite p95 (25 s) includes the load spike up to 21.5. The warm runs are the steady state of a long-lived app process.

### Where the time goes

"SQL" is the wait on the database call, including turning its rows into JS objects, which both engines do inside the call. "JS" is everything else in `recommend`.

| run | SQLite SQL p50 / p95 | SQLite JS p50 / p95 | DuckDB SQL p50 / p95 | DuckDB JS p50 / p95 |
|---|---|---|---|---|
| cold | 6.85 / 21.48 | 1.89 / 3.37 | 9.71 / 15.57 | 1.95 / 4.05 |
| warm | 6.43 / 9.99 | 1.96 / 3.33 | 9.20 / 14.46 | 1.80 / 3.47 |

- SQL takes 76–83% of a request on both engines. The JS part is the same on both (about 1.9 s at p50), as expected for the same code.
- A request runs a median of 118 statements and receives a median of **2.27 million rows** (p95 2.5 million). Most of the rows come from these statements:

  | statement (signal) | calls per request | rows per call |
  |---|---|---|
  | `SELECT filme_id, entidade_id FROM elenco_principal` (the whole view) | 2–3 | 297k |
  | the content path's `EDGES` (`signals/content.ts`) | about 16 (once per Presente and link) | up to 167k |
  | `SELECT * FROM genoma WHERE tag IN (…)` (similarity) | — | about 175k |
  | `SELECT DISTINCT filme_id FROM elenco_principal_imdb` | — | 138k |

A warm micro-benchmark (median of 5 runs) on the heaviest statements splits computing the statement (`count(*)` over it) from handing its rows to JS:

| statement | rows | SQLite count(*) | SQLite rows to JS | DuckDB count(*) | DuckDB rows to JS | DuckDB columns to JS |
|---|---|---|---|---|---|---|
| content edges, genre | 166,643 | 227 ms | 525 ms | 75 ms | 715 ms | 522 ms |
| content edges, cast | 136,581 | 314 ms | 484 ms | 99 ms | 645 ms | 569 ms |
| `elenco_principal` (whole view) | 297,196 | 617 ms | 945 ms | 86 ms | 475 ms | 273 ms |
| DISTINCT `elenco_principal_imdb` | 138,492 | 26 ms | 91 ms | 13 ms | 95 ms | 51 ms |

(2 threads. With 1 thread the numbers are within noise, and the picture is the same.)

DuckDB computes these statements 2–7× faster. But for a result of 100k+ rows, building the JS row objects takes most of the time. On the content edges, DuckDB's conversion alone (about 640 ms) costs more than SQLite's whole statement (525 ms). Only the statement that SQLite computes slowly, the view with `DISTINCT` over a join, comes out ahead on DuckDB (2×). Even DuckDB's columnar read (`getColumnsJS`, which the engine does not use) only brings the edges level with SQLite.

So the switch alone cannot reach 2×. Where SQL is about 80% of the time, the volume of rows crossing into JS sets the time, not the database engine.

### Size and memory

| | SQLite | DuckDB |
|---|---|---|
| file | 3.01 GB (3,011,444,736 B) | 1.66 GB (1,659,908,096 B), indexes included |
| peak RSS of the `recommend` process, 2 × 32 requests × 2 passes | 1.14 / 1.26 GB (rounds 1 / 2) | 1.56 / 1.55 GB, with `memory_limit` 1GB |
| process start to first request | 11–31 ms | 85–165 ms (opening the instance) |

DuckDB's file is 45% smaller. Its process peaks about 0.35 GB higher, which still fits the 1 GB cap plus the JS heap. `temp_directory` was empty after the run.

### Parity

- 120 of the 128 paired answers have the same hash. The hash compares the whole `Recommendation` JSON, with floats rounded to 12 significant digits.
- The other 8 are two requests, every time. Each has one Evidence line that names two films in a different order. The two films share a title and differ only in year.
- The content signal's `SEEDS` sorts by `s.entidade_id, n.nota DESC, f.titulo`, and that order has no tiebreak for two Notas of the same score on two films of the same title. SQLite returns its scan order and DuckDB returns another. This is a gap in the engine's SQL, not a DuckDB bug.
- The parity planned for the switch (decision 9 in #124) would catch it. The fix is to add `f.ano, n.filme_id` to the `ORDER BY`, and it holds whether or not DuckDB comes in.

## Go / no-go

**No-go against the 2× target.** At p95, DuckDB comes out at 0.78× over all runs and 0.71× warm. Only cold runs reach 1.30×, and even there it is short of 2×.

What the numbers point at instead, for whoever picks up `recomendar`'s speed. These are not measured here.

- **Cut the rows crossing into JS.** That is roughly 2.3 million per request today:
  - `elenco_principal` is read whole, 2–3 times per request. It is a catalog-wide constant, so it can be read once per process, or replaced by a query that returns only the Candidates' pairs.
  - The content path's `EDGES` ships every film linked to every entity the Pessoa rated; it could be aggregated in SQL.
- **Keep catalog-wide lookups in memory in the app process.** The catalog only changes at `db:publish`, so these lookups can stay loaded until then.
- **DuckDB could still be worth it after the SQL does the aggregating.** It wins clearly once the work is a scan, a join or a `DISTINCT`, not a transfer: 3–7× on `count(*)`. Measure it again then, with the same bench.

## Reproduce

The code is on branch `research/124-duckdb`, folder `research/124-duckdb/`. It is a throwaway prototype, outside the pnpm workspace; it imports the engine from `packages/engine/src`.

```sh
cd research/124-duckdb && npm install && ln -sfn "$(readlink -f ../../packages/engine/node_modules/effect)" node_modules/effect
# <work>: base.sqlite and base-cache.sqlite (read-only backups of the real files),
# config-en/ (migrateConfig to-en of config/), an empty dados-vazio/, duck-tmp/
node convert.ts <work>/base.sqlite <work>/base.duckdb <work>/duck-tmp
node bench.ts <work> 124 32 2 2 <work>/main.json     # seed, requests, rounds, DuckDB threads
node summarize.ts <work>/main.json
node micro.ts <work> 2 5
```

`bench.ts` writes timings and output hashes only. `worker.ts` writes the answers themselves only with `BENCH_DUMP` set (private, for chasing a difference). The full run took 45 min.
